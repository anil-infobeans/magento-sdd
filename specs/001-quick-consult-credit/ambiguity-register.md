# Ambiguity / TBD Register: Quick Consult Credit

Every unresolved issue identified while decomposing the SRS and Technical Architecture into specifications is recorded here. No unresolved decision is embedded silently in prose elsewhere in this specification set.

| ID | Issue | Source of Ambiguity | Affected Requirement(s) | Decision Required | Owner | Impact if Unresolved |
|---|---|---|---|---|---|---|
| AMB-001 | Which admin configuration surface (product attribute values, dedicated system configuration section, or catalog custom options) is used to store/manage denominations is not specified beyond "dynamically configurable." | SRS §3.1 states denominations "must remain dynamically configurable" without naming a mechanism. | QCC-PROD-004, QCC-PROD-005 | Choose the configuration surface (e.g., Magento System Configuration section vs. product custom options) during planning. | Product/Engineering | Implementation may choose an approach that is harder to extend or inconsistent with other Magento configuration conventions. |
| AMB-002 | Rounding rule for any calculation that could produce more than two decimal places is undefined. No current calculation in scope requires rounding (denominations and amounts are always exact to 2 decimals), but the rule is not stated for future-proofing. | Absence of guidance in SRS/Architecture beyond "Decimal amount with 2 decimal places." | QCC-CURR-002, QCC-CURR-003 | Confirm no in-scope calculation requires rounding; define a rounding policy (e.g., banker's rounding vs. round-half-up) if one is ever introduced. | Engineering | Low impact for v1 (no calculation currently divides/prorates an amount); becomes relevant only if a future feature introduces proration. |
| AMB-003 | **RESOLVED (2026-09-12)**. The exact qualifying Magento order/payment state that triggers purchase posting was described only by example ("e.g., invoice generated and order marked complete"), not as a definitive, single required status. | SRS §3.1, §3.3.1; Architecture §10, §19 ("must match project checkout/payment lifecycle"). | QCC-PURCHASE-001, QCC-PURCHASE-002, QCC-PURCHASE-003 | **Resolution**: Qualifying condition = invoice generated AND order status is `complete` (non-virtual orders) or `processing` (virtual orders, which do not reach `complete` via a shipment step). Recorded via `/speckit-clarify` session 2026-09-12; see [spec.md](./spec.md#clarifications) and [purchase.md](./purchase.md) QCC-PURCHASE-001/003. | Product/Engineering (order lifecycle owner) | Resolved — no remaining impact. |
| AMB-004 | **RESOLVED (2026-09-12)**. The SRS's transaction-creation API example showed only `"transaction_type": "redeem"` for external callers; the Architecture's data contract table did not explicitly enumerate which transaction types an external (non-admin) integration is permitted to submit. | SRS §4.2 example payload; Architecture §11.2 "Input" list (generic `transaction_type` field, no explicit allow-list per caller type). | QCC-API-016 | **Resolution**: External (non-admin) integrations may submit `REDEEM` only. `PURCHASE` remains system-initiated only; `ADMIN_ADD`/`ADMIN_REMOVE` remain admin-only. Recorded via `/speckit-clarify` session 2026-09-12; see [spec.md](./spec.md#clarifications) and [api.md](./api.md) QCC-API-016. | Product/Security | Resolved — no remaining impact. |
| AMB-005 | **RESOLVED (2026-09-12)**. The precise interaction between an authorization failure (caller not entitled to the target customer) and a `CUSTOMER_NOT_FOUND` response was not defined — i.e., whether the API should distinguish "customer doesn't exist" from "customer exists but you're not authorized" (which could enable customer-ID enumeration), or return a uniform denial. | SRS §4.1, §4.2 list `CUSTOMER_NOT_FOUND` and "Unauthorized -> HTTP 401" as separate, independent error scenarios without describing their interaction. | QCC-SEC-008, QCC-REDEEM-011, QCC-API-005, QCC-API-007 | **Resolution**: Authorization is checked first; an unauthorized caller always receives a uniform unauthorized/denied response regardless of whether the target customer exists. `CUSTOMER_NOT_FOUND` is returned only once authorization for the target customer is already established. Recorded via `/speckit-clarify` session 2026-09-12; see [spec.md](./spec.md#clarifications), [security.md](./security.md) QCC-SEC-008, [api.md](./api.md) QCC-API-005/007, and [redemption.md](./redemption.md) QCC-REDEEM-011. | Security/Product | Resolved — no remaining impact. |
| AMB-006 | Behavior when a state-changing request is replayed with the same `idempotency_key` but a materially different payload (e.g., different amount or customer) is not addressed by the SRS or Architecture. | Architecture §15 only describes the "same request replayed" case, not a conflicting-payload replay. | QCC-IDEMP-006 | Decide whether a conflicting-payload replay should be rejected (e.g., `IDEMPOTENCY_KEY_CONFLICT`) or treated as a new, unrelated request. | Engineering/Security | Ambiguous handling could allow a caller to silently overwrite the semantic meaning of a prior transaction under the same key, or could reject legitimate distinct operations that coincidentally reuse a key. |
| AMB-007 | **RESOLVED (2026-09-12)**. No numeric performance targets (latency, throughput) were specified anywhere in the SRS or Technical Architecture. | Absence of any SLA statement in either source document. | QCC-PERF-001, QCC-PERF-002, QCC-PERF-003, QCC-PERF-004 | **Resolution**: Approved as binding: 500ms p95 for balance retrieval and transaction-history retrieval; 1 second p95 for redemption transactions and admin balance/history view, all under nominal load. Recorded via `/speckit-clarify` session 2026-09-12; see [spec.md](./spec.md#clarifications) and [non-functional.md](./non-functional.md) QCC-PERF-001–004. | Product/Engineering | Resolved — no remaining impact. |
| AMB-008 | **RESOLVED (2026-09-12)**. Ownership and prior existence of the "Consultation Services" attribute set was assumed but not confirmed; the SRS references it as a precondition without describing who creates/maintains it. | SRS §3.1 "Must be assigned to the Consultation Services attribute set" (assumed existence). | QCC-PROD-002, QCC-PROD-002a | **Resolution**: The attribute set is created if not already present, derived from Magento's Default attribute set. Recorded via `/speckit-clarify` session 2026-09-12; see [spec.md](./spec.md#clarifications) and [product.md](./product.md) QCC-PROD-002a. | Catalog/Merchandising owner | Resolved — no remaining impact. |
| AMB-009 | No specific data-retention period for credit ledger/account records is defined. | Absence of a retention-period statement in SRS/Architecture; task instructions require neutral, non-invented compliance language. | QCC-COMPLY-001 | Business/compliance owner to define a retention period (or confirm indefinite retention) for financial-like transaction records. | Compliance/Legal | Absent a defined retention period, the implementation cannot include a defensible data-lifecycle/purge policy. |
| AMB-010 | No specific regulatory regime, jurisdiction, tax treatment, or financial-services rule is named in the SRS or Architecture as applicable to Quick Consult Credit. | Absence of any regulatory citation in either source document. | QCC-COMPLY-006 | Compliance/Legal to confirm whether any specific regulation (e.g., prepaid instrument regulations, escheatment/unclaimed-property law) applies to this jurisdiction and product structure. | Compliance/Legal | Implementing without this confirmation risks either unnecessary over-engineering or an actual unaddressed compliance gap; this specification set deliberately does not assume either. |

## Register Maintenance

- This register must be reviewed and updated at each subsequent `/speckit-clarify` or `/speckit-plan` pass for this feature.
- No item in this register may be silently resolved by an implementation choice; each requires an explicit decision recorded here (with the entry updated to reflect the resolution and superseded requirement text, if any, in the affected specification file).
